# モバイル中心ホーム画面リデザイン設計

## 目的

スマートフォンでの初回利用時に、「条件を細かく入力するアプリ」ではなく「今日のご飯を軽く決めるアプリ」と理解でき、片手で迷わずルーレットを実行できるホーム画面へ再設計する。

## 成功条件

- 初期表示でユーザーが主要CTA（「ルーレットを回す」）をすぐ発見できる。
- 料理・場所・詳細条件を、初期画面の情報量を増やさず編集できる。
- 320〜430px程度のスマートフォン幅で横スクロールや操作しづらい密集が発生しない。
- ルーレット後に結果カードが画面の主役になり、次の操作が明確になる。
- 既存の抽選ルール、履歴保存、候補生成の挙動は変更しない。

## デザイン方針

- 暖色系オフホワイトを背景、濃いブラウンを本文、テラコッタをアクセントにする。
- 親しみやすさは保つが、装飾や情報カードを増やしすぎない。
- ホームは条件編集画面ではなく、条件を確認してルーレットを開始する画面とする。
- タップ対象は片手操作を前提に、十分な高さと明確な押下状態を持たせる。
- 結果表示時は結果カードと主要アクションの視認性を最優先する。

## ホーム画面構成

初期表示は次の順序とする。

1. アプリ名または短いブランド表示
2. 「ひとり / みんなで」のモード切替
3. 「今日のご飯、どうする？」というメインメッセージ
4. 現在の条件サマリー
5. 条件を追加・編集する導線
6. 「ルーレットを回す」の主要CTA
7. 下部ナビゲーション

料理候補のチップ一覧、場所入力、詳細条件、ブランド指定は初期表示に常設せず、条件編集の操作から表示する。

## 条件編集

料理、場所、その他の条件は、スマートフォンではボトムシートまたはそれに準ずる画面内オーバーレイとして表示する。

- 背景にオーバーレイを表示し、編集中の領域へ視線を集中させる。
- シート内は縦スクロール可能にする。
- 閉じる操作を明確にする。
- 既存の `include[]`、`exclude[]`、場所、条件状態はそのまま利用する。
- 条件変更時に候補結果をリセットする既存挙動は維持する。

## 結果表示

料理結果・店舗結果ともに、結果カードを主要コンテンツとして表示する。

- 結果の見出し、対象名、補足情報、主要アクションの順にする。
- 料理結果では「この料理に決定」「この料理のお店を探す」「もう一度回す」を優先する。
- 店舗結果では「この店に決定」を最優先し、再抽選・除外・保存を続けて配置する。
- 結果生成後は、結果カードが視認できる位置へスクロールする。
- 抽選・決定・履歴保存のドメイン挙動は変更しない。

## レスポンシブ基盤

- `min-height: 100dvh` を利用する。
- 下部ナビゲーションに `env(safe-area-inset-bottom)` を反映する。
- 下部ナビゲーションがコンテンツを隠さないよう、画面下部の余白を確保する。
- 320px〜639pxでは、フォームやグループ入力を原則1列にする。
- 入力欄の文字サイズはモバイルブラウザの自動ズームを避けるため16px以上を基本にする。
- ボタン・選択項目は最低44px程度のタップ領域を確保する。
- 640px以上では、現在の中央寄せ最大幅の考え方を維持しつつ、余白と情報密度を調整する。

## 対象ファイル

主な対象は以下とする。

- `src/App.tsx`
- `src/styles.css`
- `src/components/ConditionSummary.tsx`
- `src/components/FoodPickerSheet.tsx`
- `src/components/LocationPicker.tsx`
- `src/components/ConditionPanel.tsx`
- `src/components/ResultCard.tsx`

必要に応じて `BottomNav` と関連する小さな表示コンポーネントを調整する。抽選ロジック、プロバイダー、永続化層は対象外とする。

## 検証

- `npm run build`
- 既存の `npm test -- --run`
- 320px、375px、390px、430px幅での表示確認
- 条件編集、ルーレット、結果操作、下部ナビの基本操作確認
- キーボード操作と `aria-pressed` / `role="status"` など既存アクセシビリティの維持確認

## 非対象

- 新しい料理・店舗機能の追加
- 抽選確率や候補生成ルールの変更
- アカウント、同期、PWA化
- 写真や大規模なアニメーションの追加
- 保存画面・履歴画面の全面リデザイン
