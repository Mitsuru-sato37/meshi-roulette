# ご飯ルーレット MVP基盤 設計書

## 1. 目的

料理を決めるルーレットと、料理条件に合う店舗候補から抽選するルーレットを、スマートフォン向けWebアプリとして動かす。第1段階では外部店舗APIに依存せず、リポジトリ内のマスターデータと開発用店舗データで、候補生成と抽選の境界を検証できる状態を作る。

## 2. 対象範囲

### 対象

- ホーム画面と下部3タブ（ホーム / 行きたい店 / 履歴）の土台
- `data/food-categories.json` と `data/local-specialties.json` のビルド時同梱
- おまかせ、料理の複数選択、料理除外、料理検索
- 料理候補の生成と、候補からの同確率抽選
- 店舗候補の生成と、候補からの同確率抽選
- ユーザーが明示的に設定したweightだけを反映する抽選
- 結果表示と正式決定の分離
- 設定、行きたい店、決定履歴のローカル保存
- 外部店舗検索を後から接続できるProviderインターフェース

### 対象外

- 実際の位置情報取得、地図検索、経路検索、営業時間API連携
- 本番のGoogle Places等への接続
- アカウント、クラウド同期、QR参加、リアルタイム投票
- 評価、距離、人気、履歴などによる暗黙の重み付け
- 仕様書にないおすすめロジック

## 3. 技術構成

- Vite + React + TypeScript
- 画面状態はReactの状態管理を使用し、永続化が必要な状態だけ`localStorage`へ保存する
- 料理データとご当地データは`src`からJSONをimportし、実行時のGitHub取得は行わない
- ルーレットエンジンはUI、Candidate Provider、外部APIに依存しない純粋なドメインモジュールにする
- スタイルは依存を増やさず、CSSで暖色系オフホワイトとテラコッタ系アクセントを構成する

## 4. モジュール境界

```text
UI
 ↓
Session / Application Logic
 ↓
Candidate Generator ── Provider Adapter
 ↓
Roulette Engine
 ↓
Local Persistence
```

### Master Data

JSONの構造を型付きデータへ変換し、料理の包含・除外・検索と、ご当地料理の地域参照を提供する。料理が複数カテゴリから参照されても、最終的なfoodIdは重複排除する。

### Candidate Generator

条件から抽選可能な候補集合を作る。料理候補と店舗候補の生成を分ける。第1段階の店舗Providerは固定fixtureを返すが、UIはProviderの具体実装を直接参照しない。

### Roulette Engine

候補と任意の明示weightだけを受け取り、1件を返す。weight未指定は1とする。評価・距離・人気・順位・履歴を入力しないことで、暗黙の重み付けを構造的に防ぐ。

### Session / History

抽選結果を表示しただけでは履歴へ保存しない。「料理に決定」「この店に行く」などの明示操作時にだけDecisionHistoryを作成する。再抽選では条件が変わらない限り同じ候補集合を再利用する。

## 5. 主要な状態とフロー

1. ホームで料理条件を設定する
2. Candidate Generatorが料理候補を作る
3. Roulette Engineが料理を抽選する
4. 結果を表示する。ここでは履歴を保存しない
5. 料理だけ決定するか、その料理を使って店舗候補を生成する
6. 店舗候補を一覧表示し、抽選または直接決定を選ぶ
7. 明示的に決定した場合だけ履歴へ保存する

候補数が0件の場合は抽選不可を表示し、条件を自動変更しない。1件の場合はルーレット演出を行わず、直接決定を表示する。2件以上の場合だけ通常抽選を行う。

## 6. 永続化

`localStorage`のキーはアプリ固有の接頭辞を付け、保存・読み込みに失敗してもアプリ本体がクラッシュしない。保存対象は設定、SavedRestaurant、DecisionHistoryとする。候補集合や抽選中の一時状態は永続化しない。

## 7. テスト方針

- ルーレットエンジンは、同一weightの候補、明示weight、空候補、不正weightをテストする
- Candidate Generatorは、包含・除外・複数カテゴリ参照の重複排除をテストする
- 履歴操作は、結果表示だけでは保存されず、明示決定で保存されることをテストする
- Provider境界はfixture実装を使った統合テストで、候補生成と抽選が混ざっていないことを確認する
- UIは主要フローのスモークテストを行い、0件・1件・複数件の表示を確認する

## 8. 受け入れ基準

- 料理を複数指定すると、各料理を候補として重複なく扱える
- 通常の候補はすべてweight=1で抽選される
- 明示weightだけが確率へ影響する
- 抽選結果を見ただけでは履歴が増えない
- 明示的な決定で履歴が増える
- 料理決定後に店舗候補フローへ継続できる
- 店舗候補が0件なら条件を変更せずに停止する
- 店舗候補が1件ならルーレット演出を行わない
- 同条件の再抽選で候補Providerを再実行しない
