# メシ決めルーレット 設計仕様

## 1. 目的

食事を決める際の迷いを減らし、一人でも複数人でも短時間で納得できる候補を決められる、スマートフォン優先のWebアプリを作る。

参考サイトの「開いてすぐ抽選できる簡潔さ」は受け継ぐが、画面・文章・データ構造は独自に設計する。単なるランダム抽選ではなく、複数人の希望人数とNG条件を反映できる点を主要な差別化とする。

## 2. 成功条件

- 一人利用では、初期状態から3操作程度で結果へ到達できる。
- 複数人利用では、一台の端末を囲み、おおむね1分以内に抽選できる。
- アカウント登録や参加リンクを必要としない。
- 抽選方式と当選理由が利用者に分かる。
- 候補がゼロになった場合も、行き止まりにならず条件緩和を提案する。
- スマートフォンとデスクトップの両方で操作でき、キーボード操作と読み上げにも配慮する。

## 3. 対象利用者と利用場面

### 一人利用

- 今日の食事を手早く決めたい。
- ジャンルやチェーンに強い希望はないが、予算や気分はある。
- 決定後、そのまま周辺店舗を探したい。

### 複数人利用

- 家族や友人が一台の端末を見ながら相談する。
- 回答の秘匿は不要とする。
- 共通条件、希望人数、誰か一人でも避けたい候補を画面上で入力する。
- 大人数向けのルーム、参加リンク、QRコード、個別端末投票は初版に含めない。

## 4. 主要画面と導線

アプリは一画面中心とし、詳細設定は展開式のパネルに収める。

1. ヘッダー
   - サービス名と短い説明
   - ライト／ダーク表示切替
2. 利用モード
   - 「ひとりで決める」
   - 「みんなで決める」
3. 抽選対象
   - 「ジャンルから」
   - 「チェーンから」
4. 条件設定
   - ジャンル
   - 予算
   - 気分・状況
   - 一時除外
5. 複数人設定（複数人モードのみ）
   - 人数
   - 各候補の希望人数
   - NG指定
   - 抽選バランス
6. 抽選結果
   - 決定したジャンルまたはチェーン
   - 選ばれた理由
   - Googleマップで周辺店舗を探す
   - もう一度抽選
   - 今日は出さない
7. 補助パネル
   - 条件
   - 一時除外
   - 決定履歴
   - データ管理（履歴・設定の消去）

## 5. 一人モード

初期状態ではすべての候補が対象となり、条件入力をしなくても抽選できる。利用者が条件を指定した場合のみ対象を絞り込む。

利用者は以下を任意に設定できる。

- ジャンル
- 予算帯
- 気分・状況（がっつり、軽め、早く食べたい、野菜、持ち帰りなど）

結果は直近3件の履歴を一時的に除外し、同じ候補が連続しにくいようにする。履歴除外だけで候補がゼロになる場合は、古い履歴から1件ずつ候補へ戻す。この自動緩和は利用者が明示した条件やNGには適用せず、結果画面に「新しい候補がなかったため、以前の候補を含めました」と表示する。

## 6. 複数人モード

一台の端末を全員で見ながら、会話と同時に入力する。

### 入力

- 参加人数を設定する。
- 初版で扱う参加人数は2〜8人とする。
- 共通の予算・気分・ジャンル条件を設定する。
- 共通条件を適用した候補から最大8件のショートリストを作る。9件以上ある場合は履歴回避後の対象から平等に8件を選ぶ。
- ショートリストの候補ごとに希望人数を0人から参加人数まで指定できる。
- ショートリストの候補ごとにNGを指定できる。NG候補は抽選方式に関係なく除外する。
- ショートリストは「候補を入れ替える」で再作成できる。

ショートリスト内の全候補がNGになった場合は抽選を無効にし、NGを保持したまま、ショートリスト外の有効候補から候補を入れ替える操作を提示する。ショートリスト外にも有効候補がない場合はNGを自動解除せず、一時除外・NGパネルへの導線と該当件数を表示する。

### 抽選バランス

抽選前に次の二方式から選択できる。

#### 平等に抽選

ショートリスト内でNGではない候補をすべて同じ確率とする。初期選択はこちらとし、希望人数の入力は省略できる。ルーレットらしい意外性を優先する。

#### みんなの希望を反映

ショートリスト内の候補の抽選口数を `1 + 希望人数` とする。0票の候補にも1口を残し、希望を反映しつつ完全な多数決にはしない。

### 結果説明

結果には方式と根拠を短く表示する。

- 平等抽選の例: 「NGなしの8候補から平等に抽選」
- 希望反映の例: 「4人中3人が希望。抽選確率が上がった候補です」

## 7. 候補データ

初版の候補データはアプリ内の静的データとして保持する。

初版には17種類以上のジャンルと60件以上の飲食チェーンを収録する。チェーンは全国展開または複数地域で一般利用されるものを中心とし、全件がジャンル、Googleマップ検索語、予算帯、1件以上の気分・状況タグを持つことをデータ検査で保証する。価格帯とタグは公式な保証ではなく、一般的な利用場面を想定した編集上の目安として扱う。

### ジャンル

各ジャンルは以下を持つ。

- ID
- 表示名
- Googleマップ検索語
- 対応する予算帯
- 気分・状況タグ

### チェーン

各チェーンは以下を持つ。

- ID
- 表示名
- ジャンル
- Googleマップ検索語
- 予算帯
- 気分・状況タグ

価格帯、営業時間、店舗の有無は参考情報であり、実際の情報は検索先で確認する旨を表示する。

## 8. 絞り込みと抽選処理

抽選は次の順序で処理する。

1. 選択されたジャンル、予算、気分・状況に一致する候補を残す。
2. NG候補と「今日は出さない」候補を除外する。
3. 直近履歴にある候補を可能な範囲で除外する。
4. 平等抽選または希望反映抽選を実行する。
5. 結果と抽選理由を保存し、表示する。

複数ジャンルを選んだ場合は、いずれかに一致すれば対象とする（OR）。複数予算帯もいずれかに一致すれば対象とする（OR）。気分・状況タグを複数選んだ場合は、選んだすべてを持つ候補だけを対象とする（AND）。未選択の条件軸は制限しない。

履歴除外だけで候補がゼロになる場合は、古い履歴から順に自動復帰させる。それでも候補がゼロの場合、利用者が指定した条件、NG、一時除外を自動では解除しない。解除候補を「最後に追加した気分・状況タグ」「予算」「ジャンル」の順で一つずつ提示し、利用者がボタンで明示的に解除する。NGと一時除外はこの提案対象にも含めず、専用パネルからのみ解除できる。

## 9. 状況プリセット

操作回数を減らすため、よく使う気分・状況タグを一操作で設定するプリセットを用意する。

- すぐ食べたい: `quick`
- がっつり: `hearty`
- 軽め: `light`
- ひとりで入りやすい: `solo-friendly`
- 家族・グループ: `group-friendly`
- 夜遅め: `late-night`

各プリセットは対応するタグ一つを選択し、再度押すと解除する。複数プリセットを選んだ場合は通常の気分・状況タグと同じAND条件で扱い、個別条件画面からも変更できる。初版では端末の時刻や位置情報から条件を自動変更せず、利用者の明示的な選択を優先する。

## 10. 保存とプライバシー

以下をブラウザー内に保存する。

- 表示テーマ
- 最後に使った条件
- 一時除外候補と解除時刻
- 決定履歴

サーバーへの個人情報送信、アカウント、分析用の行動追跡は初版に含めない。保存データはデータ管理パネルから消去できるようにする。

「今日は出さない」は端末のローカル時刻における次の午前0時まで有効とし、再訪時に期限切れの項目を削除する。利用者は期限前でも一時除外パネルから手動解除できる。

## 11. Googleマップ連携

結果画面から `https://www.google.com/maps/search/?api=1&query=<検索語>` を新しいタブで開く。検索語には選ばれたジャンルまたはチェーンのGoogleマップ検索語を使用し、`encodeURIComponent` 相当でURLエンコードする。リンクには新しいタブから元ページを操作できない属性を付ける。

現在地はGoogleマップ側に任せ、初版のアプリ自身は位置情報権限を要求しない。この方針により、権限要求と地理情報処理を避けながら周辺検索を実現する。

## 12. 視覚・操作設計

- モバイルファーストの一列レイアウトとする。
- 主操作は親指で押しやすい大きさにする。
- 条件チップ、抽選方式、NG状態を色だけで区別しない。
- 抽選演出は短時間とし、結果を待たせない。
- `prefers-reduced-motion` に従い、演出を省略できるようにする。
- 抽選結果、候補ゼロ、全候補NGなどの動的な状態変化はライブ領域で読み上げ、抽選完了時は結果見出しへフォーカスを移す。
- ライト／ダーク表示に対応する。
- 参考サイトの構造は研究対象に留め、コピー、配色、文章、装飾は独自にする。
- 食事を扱う消費者向けサイトとして、食欲と楽しさを支える独自のビジュアルを少なくとも1点使用する。

## 13. 初版に含めないもの

- アカウント登録、ログイン
- 参加リンク、QRコード、複数端末同期
- 独自の店舗データベース
- 店舗の口コミ、営業時間、混雑状況の取得
- 予約、注文、決済
- サーバー側での履歴保存
- 利用者の許可を必要とする位置情報取得

これらは、実利用で必要性が確認された場合に追加する。

## 14. 技術方針

- GitHub Pages等で配信できる静的Webアプリとする。
- 初版はサーバー、データベース、認証を持たない。
- 候補データと抽選ロジックを表示処理から分離し、単体試験可能にする。
- 保存データにはバージョンを付け、将来の候補追加や形式変更に対応する。
- 固定URL配下で動作するよう、サブパス配信を考慮する。
- サイト固有のファビコンを用意する。
- ソーシャル共有画像は明示的な依頼がないため初版では生成しない。

## 15. 検証とレビュー

### 機能試験

- 絞り込み、NG、一時除外、履歴回避の組み合わせ
- 平等抽選で候補の重みが等しいこと
- 希望反映抽選で抽選口数が `1 + 希望人数` になること
- 候補ゼロ時の条件緩和案
- ブラウザー保存と初期化
- Googleマップ検索URL

乱数結果そのものではなく、候補集合と重み計算を決定的に試験する。

### 操作性・視覚レビュー

- 360px、390px、768px、1280px幅でのブラウザー確認
- 初期状態から一人モードの結果を2タップ以内で出せるか
- 複数人の平等抽選は、人数設定から抽選まで6操作以内で完了できるか
- 希望反映方式では、最大8候補すべての希望人数とNGを設定しても画面を見失わないか
- 4人・8候補の希望反映方式を、初見のテスターが説明を読みながら60秒以内に抽選まで完了できるか
- すべての操作に可視ラベルまたはアクセシブルネームがあり、Tab、Shift+Tab、Enter、Spaceで主要導線を完了できるか
- 抽選結果、候補ゼロ、全候補NGがライブ領域で一度だけ読み上げられ、抽選完了後のフォーカスが結果見出しへ移るか
- 選択、NG、無効状態を色以外の文字またはアイコンでも判別できるか
- OSの動き軽減設定で抽選演出が省略されるか
- 結果と当選理由の分かりやすさ

### コード・安全性レビュー

- 実装完了後に独立したコードレビュー手順を実施する。
- 外部入力、URL生成、ブラウザー保存の扱いを確認する。
- 依存関係が増えた場合は脆弱性とライセンスを確認する。
- 公開前に本番相当ビルドをブラウザーで操作して確認する。

## 16. 公開前の受入条件

- 一人モードと複数人モードの主要導線が完成している。
- 両抽選方式が仕様どおり動作する。
- NG候補が当選しない。
- 候補ゼロ時に回復可能である。
- Googleマップ検索URLが所定形式で、検索語がURLエンコードされ、新しいタブで安全に開く。
- 360px、390px、768px、1280px幅とキーボード操作で主要導線を完了できる。
- 候補データが17ジャンル以上、60チェーン以上あり、全必須属性の検査を通る。
- 自動試験と本番ビルドが成功する。
- 操作性、コード、安全性のレビューで重大な未解決事項がない。
